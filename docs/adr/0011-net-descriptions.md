# 11. Net descriptions are stored by the API

Status: accepted

## Context
Users send a net together with a description in their own words: what the model represents, what
matters, what they are worried about. The LLM needs it, evaluation needs to know whether it helped
(`CLAUDE.md`, Evaluation), and the MCC collection offers textual descriptions for many models
(M2 seed). The description must not live only in the browser or in a conversation.

## Decision
- A **description** is an immutable text document, content-addressed like a net (ADR 0005):
  `description_id` is a hash of its text. It is stored as written (no normalization), in UTF-8.
- A net has **zero or more descriptions**, each linked to it with an **origin**: `user`, `mcc`, or
  `llm` (generated by the assistant and proposed to the user, never silently trusted). Several
  users can describe the same net differently; correcting a description adds a new one.
- The **goal** of a conversation (what the user wants checked) is not a description: it is the
  first user message of the session, an event (ADR 0008). A session references the net and,
  optionally, the description it was started with.
- API (all bodies pydantic models, errors as problem+json):
  - `POST /v1/nets/{net_id}/descriptions` with `text/plain` or `text/markdown`, returns the
    description (idempotent: same text, same id);
  - `GET /v1/nets/{net_id}/descriptions` and `GET /v1/descriptions/{description_id}`;
  - session creation takes `net_id`, `description_id` (optional) and the goal.
  The UI uploads the net (`POST /v1/nets`, PNML or JSON), then the description, then creates the session; a
  failure in between leaves only harmless, deduplicated, immutable records.
- Limits in `Settings` (maximum size, rejected when larger). Descriptions are plain text or
  Markdown shown as text; nothing in them is executed or rendered as HTML.
- A description is **untrusted data** like a place name (ADR 0009): quoted in delimited blocks in
  the prompt, never interpreted as instructions.
- The session event log records which description (and origin) the assistant was given, so that
  evaluation can compare "PNML and analysis only" with "plus description".

## Consequences
- Descriptions survive sessions and restarts, and are reusable by later sessions and by `bench/`.
- MCC descriptions and user descriptions share one mechanism; origin keeps them distinguishable.
- User-supplied nets and descriptions may be confidential: a retention and deletion policy is
  required before any shared deployment (backlog).
